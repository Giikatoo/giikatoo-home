# แผนสร้างเว็บไซต์โปรไฟล์ส่วนตัว

เอกสารนี้เป็นแนวทางเริ่มทำเว็บแนะนำตัวที่มีผลงาน ความสนใจ ข้อมูลส่วนตัว และกล่องข้อความสำหรับเจ้าของเว็บ โดยแบ่งงานเป็นระยะเพื่อให้ทดลองและตรวจสอบได้ทีละส่วน

## 1. ฟีเจอร์ที่แนะนำ

### หน้าโปรไฟล์สาธารณะ

- หน้าแนะนำตัว: ชื่อ รูปโปรไฟล์ คำแนะนำตัวสั้น ๆ และช่องทางติดต่อที่ต้องการเปิดเผย
- แท็บหรือเมนูสำหรับ **ผลงาน**, **ความสนใจ** และ **เกี่ยวกับฉัน**
- แกลเลอรีผลงาน: ภาพ ชื่อผลงาน คำอธิบาย วันที่/หมวดหมู่ และตัวกรอง
- รองรับมือถือ คีย์บอร์ด และข้อความภาษาไทยที่อ่านง่าย
- กำหนดข้อความเมื่อยังไม่มีผลงาน และข้อความแจ้งข้อผิดพลาด/กำลังโหลดให้ชัดเจน

### แบบฟอร์มส่งข้อความ

- ช่องชื่อ (เลือกได้), ข้อความ และข้อมูลติดต่อกลับ (เลือกได้ตามความจำเป็น)
- ตรวจสอบช่องที่จำเป็นและความยาวข้อความทั้งในหน้าเว็บและฝั่งเซิร์ฟเวอร์
- แสดงผลสำเร็จหรือข้อผิดพลาดโดยไม่ล้างข้อความที่ผู้ใช้พิมพ์เมื่อส่งไม่สำเร็จ
- แจ้งผู้ส่งว่าจะเก็บข้อมูลอะไรและเจ้าของเว็บจะนำข้อมูลไปใช้อย่างไร

### กล่องจดหมายสำหรับเจ้าของเว็บ

- ต้องมีหน้าเจ้าของเว็บที่ล็อกอินได้ ไม่แสดงข้อความส่วนตัวแก่ผู้เข้าชมทั่วไป
- แสดงรายการข้อความพร้อมสถานะ **ใหม่/อ่านแล้ว**
- เปิดอ่านข้อความ, ค้นหา/กรอง, ถูกใจ, เก็บถาวร และย้ายไปถังขยะ
- ยืนยันก่อนลบถาวร และมีวิธีกู้คืนจากถังขยะตามระยะเวลาที่กำหนด
- เมื่อมีข้อความจำนวนมาก ค่อยเพิ่มการแบ่งหน้าและการแจ้งเตือน

## 2. ลำดับการพัฒนาที่เหมาะกับ MVP

1. **กำหนดเนื้อหาและหน้าตา** — รวบรวมประวัติ ผลงาน และภาพที่มีสิทธิ์นำมาใช้ วาดโครงร่างหน้าเว็บก่อนลงมือ
2. **ทำหน้าโปรไฟล์แบบคงที่** — จัดเมนูและส่วนแนะนำตัวให้ครบ แล้วตรวจบนจอมือถือและเดสก์ท็อป
3. **ทำแกลเลอรีจากข้อมูลตัวอย่าง** — แยกข้อมูลผลงานออกจาก HTML เพื่อเพิ่ม/แก้รายการได้สะดวก
4. **ทำแบบฟอร์มฝั่งหน้าเว็บ** — เพิ่ม validation และข้อความสถานะ แต่ยังไม่ถือว่าบันทึกข้อความได้จริง
5. **เลือกบริการหลังบ้าน** — แนะนำให้เริ่มประเมิน Supabase สำหรับฐานข้อมูล, authentication และที่เก็บรูป หรือเลือกบริการที่ทีมคุ้นเคย
6. **ทำ API/การเชื่อมต่ออย่างปลอดภัย** — บันทึกข้อความและตรวจสิทธิ์บนระบบหลังบ้าน จากนั้นสร้างกล่องจดหมายที่ใช้ได้เฉพาะเจ้าของ
7. **ทดสอบและเผยแพร่** — ทดสอบการส่งข้อความและทุกสถานะของกล่องจดหมาย สำรองข้อมูล และทดลองบนมือถือก่อนเปิดเว็บ

ทำข้อ 1–4 เป็นต้นแบบได้โดยยังไม่สร้างบัญชีบริการ ส่วนข้อ 5–7 จำเป็นเมื่อจะเก็บข้อความจริงและเปิดให้บุคคลอื่นใช้

## 3. เครื่องมือที่ใช้

| เครื่องมือ | ใช้ทำอะไร | จำเป็นแค่ไหน |
| --- | --- | --- |
| Visual Studio Code | แก้ไข HTML, CSS, JavaScript และ Markdown | จำเป็น |
| เว็บเบราว์เซอร์และ Developer Tools | ตรวจหน้าจอหลายขนาดและดูข้อผิดพลาด | จำเป็น |
| Live Server (ส่วนขยาย VS Code) | เปิดเว็บในเครื่องและรีโหลดเมื่อแก้ไฟล์ | แนะนำสำหรับมือใหม่ |
| Git และ GitHub | เก็บประวัติการเปลี่ยนแปลงและสำรองโค้ด | แนะนำ |
| Figma หรือกระดาษร่างหน้าจอ | วางโครงร่างและเลือกสี/ตัวอักษร | เลือกใช้ได้ |
| Supabase หรือบริการหลังบ้านที่เทียบเท่า | ฐานข้อมูล, เข้าสู่ระบบ และจัดเก็บข้อมูล/ภาพ | ใช้เมื่อเริ่มทำระบบจริง |
| โฮสต์เว็บแบบ static | เผยแพร่หน้าเว็บ เช่น GitHub Pages หรือบริการ static hosting | ใช้เมื่อพร้อมเผยแพร่ |

เริ่มจาก HTML, CSS และ JavaScript ที่มีอยู่ก่อน ยังไม่จำเป็นต้องติดตั้ง framework หรือ TypeScript เพิ่ม หากภายหลังเลือกใช้ TypeScript ให้ตั้งค่า build ให้ชัดเจนก่อนนำไฟล์ไปใช้บนหน้าเว็บ

## 4. คำแนะนำสำหรับผู้เริ่มต้น

- ทำทีละส่วนและเปิดเว็บตรวจผลทุกครั้ง ไม่เริ่มจากทำหน้าแอดมินหรือระบบสมาชิกทั้งหมดพร้อมกัน
- ใช้ข้อมูลตัวอย่างก่อน อย่าใส่ข้อความจริงหรือข้อมูลส่วนบุคคลระหว่างทดลอง
- เก็บรายการผลงานเป็นข้อมูลที่แก้ไขง่าย และตั้งชื่อรูปให้สื่อความหมาย พร้อมบีบอัดภาพก่อนเผยแพร่
- แยกสถานะของข้อความให้ชัด: ใหม่, อ่านแล้ว, ถูกใจ, เก็บถาวร และถังขยะ ไม่ควรใช้สถานะเดียวแทนหลายความหมาย
- ทดสอบกรณีผิดพลาดด้วย เช่น ช่องว่าง, ข้อความยาว, ส่งซ้ำ, ไม่มีอินเทอร์เน็ต และไม่มีข้อความในกล่องจดหมาย
- ใช้ Git commit เป็นช่วง ๆ เช่น “เพิ่มหน้าโปรไฟล์” และ “เพิ่มแบบฟอร์มข้อความ” เพื่อย้อนกลับได้
- เขียนข้อความและป้ายกำกับให้เข้าใจง่าย รวมถึงตรวจการใช้งานด้วยคีย์บอร์ดและ contrast ของสี

## 5. ความเป็นส่วนตัวและความปลอดภัย

- อย่าเก็บข้อความจริงไว้ใน `localStorage` หรือไฟล์ JavaScript ฝั่งหน้าเว็บ เพราะผู้ใช้ทั่วไปเข้าถึงได้
- ห้ามใส่รหัสผ่าน, service-role key หรือ secret ไว้ในโค้ดที่ส่งไปยังเบราว์เซอร์
- ตรวจข้อมูลและจำกัดขนาดคำขอฝั่งเซิร์ฟเวอร์ รวมถึงป้องกันสแปมและการส่งถี่เกินไป
- แสดงข้อความจากผู้ใช้เป็นข้อความธรรมดา หลีกเลี่ยงการแทรก HTML ที่ผู้ใช้ส่งมาโดยตรง
- ใช้ระบบเข้าสู่ระบบและนโยบายสิทธิ์ฐานข้อมูลที่อนุญาตเฉพาะเจ้าของอ่านข้อความ/จัดการกล่องจดหมาย
- ใช้ HTTPS และกำหนดแนวทางเก็บรักษา ลบ และสำรองข้อมูลก่อนเปิดรับข้อความจริง

## 6. โครงสร้างโฟลเดอร์

```text
giikatoo-home/
├── index.html
├── README.md
├── assets/
│   ├── css/
│   │   └── style.css
│   ├── images/              # เพิ่มรูปโปรไฟล์และผลงานเมื่อพร้อม
│   └── js/
│       └── script.js
├── docs/
│   └── FEATURE-PLAN.md
└── src/
    └── script.ts            # ตัวอย่าง TypeScript; ยังไม่ได้ build หรือโหลดโดยหน้าเว็บ
```

โครงสร้างนี้คงหน้าเว็บ HTML ไว้ที่ root เพื่อให้เปิดได้ง่าย และแยกไฟล์ตามหน้าที่ สำหรับตัวอย่างนี้ `index.html` ใช้ `assets/js/script.js` ส่วน `src/script.ts` เป็นไฟล์ตัวอย่างที่ยังไม่เชื่อมต่อ ไม่ควรแก้สองไฟล์ให้เป็นแหล่งข้อมูลคนละชุด หากจะใช้ TypeScript จริงให้เพิ่มขั้นตอน compile และกำหนดไฟล์ JavaScript ที่สร้างขึ้นให้แน่นอน
